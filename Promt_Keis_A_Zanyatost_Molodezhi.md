# ПРОМПТ ДЛЯ РАЗРАБОТКИ MVP
## Хакатон NEXUS30 — Трек GovTech — Кейс A
### «Система мониторинга занятости и маршрутизации молодёжи»

---

## РОЛЬ

Ты — опытный fullstack-разработчик и продуктовый архитектор, помогающий команде за ограниченное время хакатона (24–48 часов) собрать работающий кликабельный прототип (MVP) цифровой платформы. Приоритет — рабочий, визуально убедительный прототип, а не production-система.

---

## КОНТЕКСТ И СМЫСЛ ПРОЕКТА (из официальной документации хакатона)

**Партнёр:** идёт согласование с хокимиятом Мирзо-Улугбекского района (официально не подтверждено).

**Проблема:**
На уровне махалли и района отсутствует единое, систематизированное и регулярно обновляемое представление о текущем статусе занятости совершеннолетней молодёжи — работает ли человек, каким видом деятельности занимается, как меняется его статус, нуждается ли в поддержке.

Из-за разрозненного ведения данных сложно оценивать реальную занятость молодёжи, своевременно выявлять безработных или молодых людей, выпавших из процессов обучения и занятости (NEET), и планировать меры поддержки.

Ответственному сотруднику нужен не просто статистический показатель, а **управленческий инструмент**: видеть ситуацию в разрезе территории, выделять приоритетные группы, определять дальнейшие действия.

**Цель:** разработать концепцию цифровой платформы/дашборда, которая систематизирует, обобщает и отслеживает статус занятости молодёжи на уровне махалли и района, а также помогает выявлять тех, кто нуждается в поддержке.

## ЦЕЛЕВАЯ АУДИТОРИЯ

- уполномоченные сотрудники на уровне махалли;
- представители махалли, ответственные за работу с молодёжью;
- уполномоченные сотрудники районного хокимията;
- специалисты в сфере занятости молодёжи и социальной поддержки.

---

## ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ (полный список из документации)

1. **Ведение статуса занятости в единой системе** — для каждого демо-профиля: занят/не занят, вид деятельности (работа/обучение/предпринимательство/иное), дата последнего обновления, наличие потребности в поддержке.

2. **Обобщённый мониторинг по махалле и району** — сводное представление: занятая молодёжь, безработные, лица с неуточнённым статусом, NEET, кандидаты на программы поддержки. Индивидуальные карточки + агрегированная картина.

3. **Выявление NEET и ситуаций, требующих внимания** — выделение в отдельную категорию молодых людей вне работы/учёбы/деятельности. **Важно:** система НЕ присваивает окончательный статус автоматически — только помечает как «требует проверки уполномоченным сотрудником».

4. **Рекомендация направлений поддержки** — модуль-подсказка (не автоматическое решение): трудоустройство, профобучение, переподготовка, предпринимательство, возврат к обучению.

5. **История изменения статусов** — трек по времени, например: «безработный → направлен на обучение → трудоустроен».

6. **Территориальная визуализация** (опционально/бонус) — карта состояния занятости по махаллям в агрегированном виде, без точных адресов реальных лиц.

---

## ОГРАНИЧЕНИЯ (обязательно учитывать в архитектуре и в демо)

- Используются **только демо/синтетические данные** — никаких реальных Ф.И.О., телефонов, адресов, персональных данных.
- Ролевой доступ: только уполномоченные пользователи видят данные в рамках своих полномочий и территории.
- Статусы «группа риска» / «NEET» — это **рекомендация к проверке**, а не финальное административное решение. Это нужно явно показать в UI (например, кнопка «подтвердить/отклонить» рядом с автоматической меткой).
- Заложить принципы конфиденциальности и информационной безопасности на уровне архитектуры (можно ограничиться концептуальным упоминанием в MVP).

## ЗАДАЧА: СПРОЕКТИРОВАТЬ И РЕАЛИЗОВАТЬ MVP

### Приоритизация скоупа (что обязательно, что бонус)

**Обязательное ядро MVP:**
- Список/таблица молодых людей с фильтрами по статусу занятости
- Карточка отдельного человека с полным набором полей (статус, вид деятельности, дата обновления, потребность в поддержке)
- Автоматическое выделение NEET-категории с флагом «требует проверки» и возможностью подтвердить/отклонить
- Модуль рекомендаций (простое правило: если статус = «безработный», предложить 2-3 релевантные меры поддержки)
- Сводный дашборд по махалле/району (агрегированные метрики: сколько занято, сколько NEET, сколько направлено на поддержку)

**Желательно, если останется время:**
- История изменения статуса (простая хронология в карточке)
- Карта/тепловая карта по махаллям
- Переключатель роли (сотрудник махалли / сотрудник района), меняющий масштаб видимых данных

**Не делать:**
- Реальную интеграцию с госсистемами или базами данных
- Полноценную систему аутентификации — переключатель роли можно имитировать UI-селектором
- Сложную ML-модель для рекомендаций — достаточно понятных бизнес-правил (if/else)

### Технические указания для реализации

1. **Стек:** фронтенд-приложение (React предпочтительно), без необходимости в реальном бэкенде — все демо-данные хранятся в статичном JSON, генерируемом заранее (25–40 синтетических профилей молодых людей с разными статусами).

2. **Модель данных** (предложи и используй структуру, аналогичную):
```json
{
  "id": "y_001",
  "full_name_demo": "Демо Профиль 1",
  "makhalla": "Демо-махалля 1",
  "age": 22,
  "employment_status": "занят" | "безработный" | "обучается" | "предприниматель" | "не уточнено",
  "activity_type": "строительство" | "IT" | "образование" | "...",
  "is_neet": true | false,
  "needs_support": true | false,
  "support_recommendation": ["профобучение", "трудоустройство"],
  "last_updated": "2026-06-01",
  "status_history": [
    {"date": "2026-01-10", "status": "безработный"},
    {"date": "2026-03-15", "status": "направлен на обучение"},
    {"date": "2026-06-01", "status": "трудоустроен"}
  ]
}
```

3. **Экраны для реализации:**
   - Экран входа (упрощённый, можно заглушку с выбором роли)
   - Главный дашборд (агрегированные показатели + фильтры по территории)
   - Таблица/список молодёжи с фильтрами (по статусу, по махалле, по флагу NEET)
   - Карточка отдельного профиля (детали + история + рекомендации + кнопка подтверждения флага)
   - (Бонус) карта территорий с агрегированной раскраской по уровню занятости

4. **Демо-сценарий, который должен безупречно работать на защите:**
вход в систему → выбор территории → просмотр статусов молодёжи → выявление группы, требующей внимания (NEET) → просмотр рекомендованного направления поддержки → (бонус) переход к карте.

### Формат ответа, который мне нужен от тебя

1. Предложи детальную архитектуру приложения (компоненты, страницы, поток данных).
2. Сгенерируй полный синтетический датасет (30–40 записей) в формате JSON согласно модели данных выше, с разумной вариативностью статусов и историй.
3. Напиши рабочий код MVP (React, без бэкенда, все данные из локального JSON) для перечисленных экранов.
4. Дай рекомендации по визуальному стилю: чистый, официальный, но современный государственный UI (не перегруженный, понятные цветовые индикаторы статусов — зелёный/жёлтый/красный).
5. Подготовь краткий план демонстрации (питч на 2–3 минуты), который явно закрывает все пункты требований и критериев оценки жюри.
